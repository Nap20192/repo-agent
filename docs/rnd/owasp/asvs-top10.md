### 1.1 Field proposal: `asvs_id` on Threat and VulnClass

```python
class VulnClass(_Model):
    cwe: str
    wstg_id: str = ""
    asvs_id: str = ""      # "8.2.2" — one requirement, the most specific
    asvs_level: int = 0    # 1|2|3 from the requirement table; 0 = unknown
    why: str = ""

class Threat(_Model):
    ...
    asvs_id: str = ""
    asvs_level: int = 0
```

`asvs_level` becomes a priority signal in `from_threats`: L1 +10, L2 +0, L3 −10 (L1 = "minimum for every app",
so an unmet L1 is the most credible threat). Keep `priority` as the model's own estimate; the bonus is additive.

## 2. ThreatModeler as an ASVS walk

Today the ThreatModeler freely invents threats per symbol. Replace "which threats apply" with a bounded
enumeration: per trust boundary, walk the *applicable* ASVS requirements (the static subset of section 1,
filtered by what the ArchitectureModel shows: a DB entity → 1.2.4; a shell/exec sink → 1.2.5; cookies → 3.3.x;
file paths from input → 5.3.2; object-by-id handlers → 8.2.2; JWT parsing → 9.1.x; crypto imports → 11.x) and
emit a threat **only** for a requirement the model cannot show satisfied.

Prompt fragment (append to `THREAT_MODELER_INSTRUCTION` after the grounding gate):

```
ASVS walk (bounded enumeration — do not invent classes outside it):
For each trust boundary, take the ASVS 5.0 requirements that apply to what crosses it, in this order:
 1.2.4 SQL/NoSQL parameterized  1.2.5 OS command  1.2.1 output encoding  1.3.2 eval  1.3.6 SSRF allowlist
 1.5.1 XML parser  1.5.2 deserialization  5.3.2 file paths  5.2.2 upload type  8.2.1 function-level authz
 8.2.2 object-level authz (IDOR)  3.5.1 CSRF  3.7.2 redirect allowlist  3.3.1/3.3.4 cookie attrs
 7.2.3/11.5.1 CSPRNG tokens  9.1.1-9.2.3 JWT signature/alg/aud/exp  11.3.2/11.4.1 approved crypto
 12.3.2 TLS cert validation  13.3.1 secrets not in source  15.3.3 mass assignment  15.3.6 prototype pollution
 16.4.1 log injection  16.5.1/16.5.3 error handling
For each requirement: if the ArchitectureModel (entities, boundaries, notes) SHOWS the control is in place
(e.g. "uses sqlc parameterized queries"), record it in `satisfied` and emit no threat. If it shows the control is
absent, or says nothing, emit ONE threat with the requirement's CWE, `asvs_id`, `asvs_level` and the symbol of the
boundary. Never emit a threat for a requirement that does not apply to anything the model describes.
Fail closed: a boundary with no applicable requirement in the list is a note, not a threat.
```

JSON extension (ThreatModel):

```json
{"threats":[{"cwe":"CWE-639","asvs_id":"8.2.2","asvs_level":1,"claim":"...","symbol":"getOrder","file":"","wstg_id":"WSTG-ATHZ-04","priority":80}],
 "satisfied":[{"asvs_id":"1.2.4","symbol":"db.Query","evidence":"sqlc generated parameterized queries"}],
 "notes":[...],"intent":"production"}
```

`satisfied[]` is new and is the key to coverage (section 3): it is the model's assertion that a requirement is
met, which the Critic can later attack (an assertion cited by a symbol is a valid disproof target).
Fail-closed rules: `satisfied` entries must cite a `symbol` from the ArchitectureModel (else dropped to notes,
like threats); `threats` and `satisfied` cannot share `(asvs_id, symbol)`; an `asvs_id` outside the static set is
kept but does not count for coverage.

Cost: the list is ~25 items → the walk stays inside one activation; `THREAT_MODELER_MAX_MODEL_CALLS=6` is enough
because the ThreatModeler has only `consult_owasp` (extend it to return `asvs_id/level` so no extra tool is needed).

## 3. Coverage reporting: "surface covered" in summary.json

New `coverage` block, computed at finish (data already exists: entry points from `entry_points_fn`, hypotheses per
round, dossiers, threat_model artifact):

```json
"coverage": {
  "entry_points": {"total": 20, "examined": 7, "by_baseline": 3},
  "anchors": {"total": 68, "examined": 24},
  "asvs": {"applicable": 14, "threatened": 6, "satisfied": 5, "unaddressed": 3,
           "unaddressed_ids": ["3.5.1", "16.5.1", "13.3.1"], "by_level": {"1": [9, 8], "2": [5, 3]}},
  "top10": {"2025": ["A01", "A05", "A07"], "2021": ["A01", "A03", "A07"]},
  "rounds": 3, "queue_left": 13
}
```

Definitions:
- `entry_points.examined` = entry points whose symbol or file appears in any investigated hypothesis (`reads`,
  `symbol`, or the anchor's file) — this is exactly what `Reconciler.coverage()` computes as *un*covered; store its
  complement. `by_baseline` = those examined only through the baseline `entry` hypotheses.
- `anchors.examined` = anchors with a hypothesis in any round (queue drained ⇒ total; round limit ⇒ partial). This
  number turns "stop_reason: round limit" into a measurable statement.
- `asvs.applicable` = distinct `asvs_id` in `threats ∪ satisfied`; `threatened` = with a threat; `satisfied` = in
  `satisfied[]`; `unaddressed` = in the static list of section 2, applicable by the ArchitectureModel signals
  (DB entity, cookies, JWT, …) but in neither list — computed deterministically from `vuln_classes` + a small
  signal→asvs table, so the model cannot hide a requirement by not mentioning it. `by_level` = [applicable, covered]
  per level.
- `top10` = categories of confirmed findings' CWEs (both editions from the corpus lists; 2025 first).

Feed: `PipelineV2._run_async_impl` already has `entry_points_fn()`, `done`, `queue`, the artifacts; write
`coverage` as an artifact next to `timings` and let `store.write_summary` include it (same pattern). ~40 lines.
`queue_left` and `entry_points.examined/total` are also the honest stop signal Shannon's plan stage asks for:
stop when both are exhausted, not when the round counter says so.

### 4.2 Should calibrate.py impact follow Top10 category or ASVS level?

| Driver | Pro | Con | Decision |
|---|---|---|---|
| Top10 category | matches how customers read reports; stable | categories are risk *buckets*, not severity: A01 spans CWE-200 (info leak) and CWE-639 (IDOR) | report-only tag, never the impact number |
| ASVS level | L1 = "every app must", so an unmet L1 requirement is the strongest signal; requirement text tells the Critic what the control looks like | levels are assurance effort, not blast radius (7.4.4 "logout link visible" is L2) | **use as a Likelihood modifier, not Impact** |
| Current CWE-class impact table (Shannon) | blast radius, already calibrated | hand-maintained | **keep for Impact** |

Concrete: `likelihood` gains `+1` when `asvs_level == 1` and the finding is confirmed (cap stays 3 for a static
engine → make the static cap 4 for L1: "the baseline control is missing" is the one case where a static finding is
as likely as an empirical one), `−1` for L3. `top10_2025` becomes a field in the calibration dict for reporting.
